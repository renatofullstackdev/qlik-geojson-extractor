# Chrome extension architecture

The Chrome extension is a UI shell around the existing browser-first extractor. It does not reimplement QIX logic.

## Components

```text
Toolbar action click
        │
        ├── records the invoked tab
        └── opens Side Panel
                 │
                 │ user grants exact Qlik host
                 ▼
          Chrome Side Panel
                 │
                 │ chrome.scripting.executeScript
                 ▼
          authorized Qlik tab — MAIN world
                 │
                 ├── chrome-extension/core/qlik-geojson-extractor.js
                 │     generated copy of browser/qlik-geojson-extractor.js
                 │
                 └── Qlik Engine / QIX
                       ├── CSRF token
                       ├── WebSocket
                       └── session hypercubes
```

`chrome-extension/core/qlik-geojson-extractor.js` is generated by `npm run build`; it must not become an independently maintained fork of the browser bundle.

## Why execute in the page MAIN world

The console workflow succeeds because CSRF retrieval and the Engine WebSocket execute from the authorized Qlik page. The extension preserves that property by injecting the same core bundle into the authorized Qlik tab with `chrome.scripting` and `world: "MAIN"`.

The Side Panel itself does not perform Qlik data requests.

## Host-access model

Programmatic script injection requires permission for the page host. Relying only on `activeTab` was fragile for a Side Panel workflow because the panel continues to issue privileged calls after the original toolbar action.

The extension therefore separates **tab selection** from **host authorization**:

1. `chrome.action.onClicked` identifies the tab the user explicitly invoked and opens the Side Panel;
2. the page URL is stored temporarily in `chrome.storage.session`;
3. the Side Panel derives an exact host match pattern from that URL;
4. the user clicks **Permitir acesso a este site**;
5. `chrome.permissions.request()` requests only that host;
6. only after permission is confirmed does the extension inject the QIX core.

The manifest contains:

```json
"optional_host_permissions": [
  "https://*/*",
  "http://*/*"
]
```

This is a declaration of what may be requested later, not an install-time grant. The extension requests a subset such as `https://example.test/*` at runtime.

There is no `host_permissions` declaration and no `<all_urls>` grant.

## Named permissions

- `activeTab`: associates an explicit toolbar invocation with the current tab and exposes its URL for that invocation;
- `scripting`: injects the generated core and command wrapper after host authorization;
- `sidePanel`: provides the persistent UI;
- `storage`: saves extraction configurations and transient tab context;
- `downloads`: saves the generated GeoJSON.

## Navigation behavior

A granted host permission remains valid for other apps and sheets on the same host. If the associated tab navigates to another origin, the extension refuses to reuse the previous authorization. The user must invoke the extension on the new page and explicitly grant that host.

## Data handling

`inspect()` retrieves field metadata, cardinalities, tags and source-table names. Record values are fetched only after the user explicitly chooses an entity key and extraction fields.

The extension stores configuration only. Generated GeoJSON and extracted record values remain in memory until downloaded or the Side Panel is destroyed; they are not persisted with `chrome.storage`.

## Semantic safeguard

The UI deliberately leaves `entityKey` unselected after inspection. Candidate keys may be ranked and displayed, but the user must make an explicit choice before extraction.

This preserves the rule demonstrated by the public TRE-DF example: a map display dimension can aggregate multiple physical spatial entities.

## URL detection

The Side Panel recognizes URLs shaped like:

```text
[/virtual-proxy]/sense/app/<APP_ID>/sheet/<SHEET_ID>/...
```

The prefix before `/sense/app/` is passed to the QIX client as `virtualProxyPath`. If the URL cannot be recognized, IDs remain editable and can be supplied manually.

## Effective extraction configuration

The Side Panel exposes the exact configuration passed to `extract()` before execution. Coordinate controls are field selectors populated from `inspect().fields`; the detected PointLayer fields are preferred but never represented as free-form text.

Custom property expressions are represented separately from direct field aggregations and are merged only when the final extraction configuration is built. This allows the Side Panel to reproduce the same `label + expression` objects supported by the core API.

## Deterministic core injection

The extension always injects `chrome-extension/core/qlik-geojson-extractor.js` before executing a Qlik command. It deliberately does not trust a pre-existing `globalThis.QlikGeoJSONExtractor` because that global may have been created by a stale DevTools bundle. Side Panel behavior therefore depends only on the version shipped with the loaded extension.

## Empty-result safeguard

A technically valid `FeatureCollection` with zero features is not considered a successful operational extraction when the hypercube contains real entity keys and every entity is reported in `missing`. In that case the Side Panel shows an error, preserves diagnostics, and disables download until the coordinate configuration is corrected.
