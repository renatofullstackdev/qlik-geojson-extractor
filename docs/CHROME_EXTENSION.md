# Chrome extension architecture

The Chrome extension is a UI shell around the existing browser-first extractor. It does not reimplement QIX logic.

## Components

```text
Chrome Side Panel
  chrome-extension/sidepanel/
        │
        │ chrome.scripting.executeScript
        ▼
active Qlik tab — MAIN world
        │
        ├── chrome-extension/core/qlik-geojson-extractor.js
        │     generated copy of browser/qlik-geojson-extractor.js
        │
        └── Qlik Engine / QIX
              ├── CSRF token
              ├── WebSocket
              └── session hypercubes
```

`chrome-extension/core/qlik-geojson-extractor.js` is generated by `npm run build`; it must not become an independently maintained fork of the browser bundle.

## Why execute in the page MAIN world

The console workflow already succeeds because CSRF retrieval and the Engine WebSocket execute from the authorized Qlik page. The extension preserves that property by injecting the same core bundle into the active Qlik tab with `chrome.scripting` and `world: "MAIN"`.

The Side Panel itself does not attempt cross-origin Qlik requests.

## Permissions

The manifest intentionally avoids persistent host access.

- `activeTab`: temporary access after explicit invocation by the user;
- `scripting`: injects the core and one command function into the active tab;
- `sidePanel`: provides the persistent UI;
- `storage`: saves extraction configurations by origin/app/sheet;
- `downloads`: saves the generated GeoJSON.

There is no `<all_urls>` and no `host_permissions` declaration.

## Data handling

`inspect()` retrieves field metadata, cardinalities, tags and source-table names. Record values are fetched only after the user explicitly chooses an entity key and extraction fields.

The extension stores configuration only. Generated GeoJSON and extracted record values remain in memory until downloaded or the Side Panel is destroyed; they are not persisted with `chrome.storage`.

## Semantic safeguard

The UI deliberately leaves `entityKey` unselected after inspection. Candidate keys may be ranked and displayed, but the user must make an explicit choice before extraction.

This preserves the rule demonstrated by the public TRE-DF example: a map display dimension can aggregate multiple physical spatial entities.

## URL detection

The Side Panel recognizes URLs shaped like:

```text
[/virtual-proxy]/sense/app/<APP_ID>/sheet/<SHEET_ID>/...
```

The prefix before `/sense/app/` is passed to the QIX client as `virtualProxyPath`. If the URL cannot be recognized, IDs remain editable and can be supplied manually.
